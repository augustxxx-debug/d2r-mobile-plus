# 诊断上传与自动上报崩溃

[English](DIAGNOSTICS.md)

这份说明告诉玩家这两个功能上传什么、什么时候上传、怎么关，并记录客户端与服务端的约定。公开包里地址由构建注入；源码里没有服务器地址和密钥。没有配置地址的构建（包括自己编译的包）不会联网。

## 两个入口

| | 分享诊断日志 → 上传报告 | 自动上报崩溃 |
|---|---|---|
| 位置 | 暂停菜单 | 选项 → 自定义（缺省关） |
| 什么时候发 | 每次由玩家在提示框里点「上传报告」 | 打开开关并在确认框里同意后，某次启动发现上一局异常退出（闪退、卡死、内存不足、原因不明的退出） |
| 有没有提示 | 提示框显示结果和报告编号 | 选角页显示一行结果，约 20 秒 |

切到后台后被系统回收、自己从多任务划掉都不算异常退出。开发和测试时带测试环境变量的局不会自动上报。

## 上传的内容

一份报告就是一段文本加六项元数据。自动上报的文本依次是：

- 第一行标明版本：`D2R Mobile Plus crash report (automatic, full)`（完整版）或 `(automatic, summary)`（摘要版）。
- 崩溃围栏状态一行，比如 `fence cause=crash arg=11 streak=2 hist=11`（原因、信号或秒数、连续次数）。
- GPU 名称（iOS；安卓在日志的 `NVN caps` 行）。
- 版本、构建号、机型、系统版本、电量与低电量模式、温控档位、可用存储、已运行时长、物理内存。
- 图形设置和「选项 → 自定义」各开关的当前值。
- 上一局和本局日志的尾部，每份最多 128 KiB（iOS）；安卓整份不超过 256 KiB，超出时保留开头和结尾。
- 系统崩溃诊断：iOS 是 MetricKit 最新一份，可能晚一次启动才送达，所以有时这份报告里没有；安卓是 `ApplicationExitInfo` 最近 5 条的退出原因和状态码，不含崩溃栈。

六项元数据是 `app_version`、`build`、`source_revision`、`model`、`os_version`、`locale`。安卓的 `model` 目前填 `unknown`，真实型号在日志头里。

## 不上传的内容

- 存档内容、截图、账号、联系人、位置。
- 设备名、UDID、容器 UUID、团队号、用户名、本机路径、邮箱、IP 地址、网址、角色名。上传前在本机抹掉，服务端还会再抹一次，但客户端不依赖它。
- 带令牌、票据、口令、私钥字样的整行。

脱敏是按规则匹配的，不能保证抹掉任何可能出现在日志里的个人信息，比如你自己写进角色名以外位置的内容。报告生成后存在 `dm_crash_report.payload`（iOS 在「文件」App 的本 App 文件夹，安卓在应用私有目录），上传成功或放弃后删除。iOS 玩家可以打开这个文件核对实际内容。

## 身份、频率与保留

- 每个安装生成一把只用于诊断的 Ed25519 钥匙，与联机身份无关。iOS 存钥匙串（只留本机，不同步），安卓存不随备份走的私有目录。服务端能看出两份报告来自同一安装，但钥匙不关联账号。
- 一次启动最多试 3 次（启动 20 秒后、在主菜单停够 5 秒、等过这次的更新清单（最多 60 秒）才开始，之后隔 60 秒和 300 秒，服务端要求更久就按它），最多跨 3 次启动、共 6 次、存放 7 天，到上限就删除报告并提示一次。服务端明确拒收不重试。
- iOS 的低数据模式下不自动上传。手动上传不受此限。
- 关掉开关并点「应用」：取消进行中的上传，删除待传报告。
- 服务端保留天数由服务端在每次上传前告知，当前为 7 天；只有授权的维护者能读取。

## 什么时候发、在什么网络下发

只在主菜单或选人页连续停留 5 秒后发，局内不发请求。如果到点时已经在局内，报告先打好存在本机，回主菜单再发。

蜂窝、低数据模式和计量网络下只发摘要版：报告开头的围栏状态、版本、设置和关键读数，不超过 16 KiB，第一行是 `D2R Mobile Plus crash report (automatic, summary)`。完整版（含日志尾部和系统崩溃诊断）只在 Wi-Fi 下发，第一行是 `(automatic, full) summary_of=<摘要的 upload_id>`，用另一个 `upload_id`。设置里没有另外的开关。摘要到了以后如果一直没有 Wi-Fi，完整版存放 7 天后删除。

## 服务端总开关

更新清单可以带 `telemetry`：`{"enabled": false, "pause_until": <Unix 秒，可选>, "reason": "<可选>"}`，缺省为开。读到 `false` 时这次启动不上传任何报告，不弹提示；异常退出的报告照常打好存在本机，受 7 天上限约束；恢复后接着发。清单拉不到就沿用上次的值。这个开关只能让客户端少发，不能让它多发，所以清单不签名也可以接受，玩家自己的开关仍是前提。上传接口回 503 + Retry-After 也当暂停：不占重试次数，至少隔 300 秒再探，一次启动最多探 3 次。玩家在暂停菜单手动点的上传不受这个开关拦，服务端可以直接回 503。

## 协议

前缀 `/diagnostics/v1`。与联机协议共用同一份服务端约定（联机线的 `docs/COOP_PROTOCOL.md` 第 7 节），这里没有新增字段。

1. `GET /diagnostics/v1/challenge` 返回 `{"challenge", "expires_in", "max_payload_bytes", "retention_days"}`。挑战单次使用，每次尝试都重取。
2. 载荷是 UTF-8 JSON：`{"schema": 1, "metadata": {六项}, "log": <脱敏文本>}`，上限 600 KiB。
3. 签名内容：`"D2R-DIAGNOSTICS-V1\n" + challenge + "\n" + upload_id + "\n" + hex(sha256(载荷)) + "\n"`。
4. `POST /diagnostics/v1/reports`，请求体正好五个字段：`public_key`、`challenge`、`upload_id`（32 位十六进制）、`payload`（base64url）、`signature`。同一 `upload_id` 重传是幂等的。
