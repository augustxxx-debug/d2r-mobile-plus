# Plus 构建与验证说明

[English](PLUS.md) · [项目概览](../README.zh-CN.md) · [更新日志](../CHANGELOG.zh-CN.md)

## 范围与原理

Plus 修改兼容层及构建时的 UI 生成器，不改写输入的原始游戏文件。构建期间，生成器读取玩家自己的资源，在被忽略的构建目录中生成覆盖层和打包资源。应用将这些生成资源与原版游戏数据配合使用。

前端场景覆盖与界面坐标分别处理。底部控件根据可用屏幕几何布局；保留游戏内原有坐标打包方式。布局覆盖限定在触控／手柄根节点，不对所有共享面板进行整体改写。

两类右下角标志分别处理：多图层火焰字样与红色存档标志。先在隐藏状态下初始化位置，再显示，避免加载切换时先出现一帧尚未定位的图像。

### 任务语音行为

基线版本的运行消息区分任务选择、语音播放和对话结束。快速第二次点击会发出结束事件。原地按住 0.8 秒后松手没有产生点击，因为移动触控识别器拒绝达到或超过普通 0.35 秒点击时限的操作。

Plus 仅允许原版／资料片任务日志根节点下的任务图标、重播控件和关闭目标使用更慢的原地松手。语音状态仍由游戏处理。拖动、取消、物品交互和无关按钮保留原有手势规则。结论来自修改前后的实机消息对照，并非独立零售版 Switch 对照测试。

## 可选字体

此功能为实验功能，仅在设置 `DM_UI_FONT` 时启用。请自行提供有权使用的静态 TrueType 字体。仓库不包含 ARKai_T。本地已使用 AR ZhongkaiGBK Medium 核对字体身份，并在实机检查中文设置页显示；这不代表所有文字和布局均已验证。字体在构建时替换，游戏内没有字体切换开关。

在资源生成所用的同一个 Python 环境中安装可选依赖：

```sh
python3 -m pip install -r dm/ios/tools/requirements-fonts.txt
export DM_UI_FONT='/path/to/your/font.ttf'
cd dm/ios
./run.sh build
```

将变量传给构建进程，或写入私有构建环境。不要提交字体或本机配置。取消 `DM_UI_FONT` 后，构建使用原字体，并清理旧的可选字体产物。

生成器统一每 em 单位，保留原版纵向度量和注册名称，并从原游戏字体补齐缺失的 Unicode 字符。不覆盖输入文件。更换字体内容会通过指纹使已生成文字失效并重建。产物位于被忽略的 `Gen/assets/UIFonts` 及生成的资源覆盖层中。

覆盖范围：共享的 `BlizzardGlobal-V5_81.ttf` 字体、使用该字体生成的文字及原生秘境 HUD 字体加载器。其他装饰字体、经典位图文字和烘焙在游戏图片中的文字不在此次范围内。保留纵向度量不保证字宽相同；实际字体仍需在中英文和不同屏幕布局下检查换行、回退字形及裁切。

合成字体测试覆盖 Unicode 缺字回退、每 em 单位转换、原版注册名称／纵向度量、输入文件不变、内容指纹、关闭后清理及无效路径。另覆盖自定义竖排表兼容与游戏原有私用区图标保留。再加下面的字重档位（自选字形变粗、字宽／行度量／回退字形／图标不变、档位单调、0 档恒等、指纹与非法取值），合计 9 项测试；实机已检查中英文图形／自定义页，完整面板回归仍待补齐。

### 字重

状态：已实现并通过单测；在 Mac 上出过样张；**3 档已在 iPhone Duo 上验收**（2026-10-27，目视启动与角色页；完整面板覆盖仍待补）。

自选字体可在构建时按档加深：`DM_UI_FONT_WEIGHT=0..8`（缺省 0 = 字体自身轮廓）。目的是把反走样后发灰的细笔画填实，不是做粗体：每档只把每一笔描边加宽 5‰ em（20 px 字号下每笔约 0.1 px），算法是 FreeType `FT_Outline_EmboldenXY` 的点位外推法，在 `dm/ios/tools/font_override.py` 里直接作用于轮廓；加粗后轮廓回中，字宽（advance）、左右边距之和与原版行高度量都不变，由游戏原字体补齐的字形（含私用区图标）一律不动。合成结果仍是普通静态 TrueType，游戏的运行时栅格化和原生秘境 HUD 加载器都自然带上字重，不需要改代码。换档会重新计算指纹，生成字体与文字一并重建。

按 AR ZhongkaiGBK Medium 标定（横竖笔画约 35–60‰ em，20 px 渲染）：0 档平均覆盖率 0.45，原版 `BlizzardGlobal` 为 0.58；2–3 档（0.50–0.52）把细笔画填实而字形仍明显是楷体；6 档（0.59）黑度追平原版，但已经是粗体观感——早先按 16‰ 一档标定时在 Mac 上实跑过，被认为太粗而否决；8 档留给特别细的字体，龘 之类密集字会糊。Mac 实跑在角色选择页对比过 2 档、4 档和早先的 32‰：2 档小字仍发灰，32‰ 像粗体，4 档（20‰）在 1280x720 窗口里合适。到 iPhone Duo 内屏（约 490 ppi，文字像素数约为前者两倍）4 档就显得太深，最终 3 档（15‰）被接受。这款字体在高密度屏上从 3 档起；笔画更粗的字体用 2 档。

```sh
export DM_UI_FONT='/path/to/your/font.ttf'
export DM_UI_FONT_WEIGHT=2
cd dm/ios && ./run.sh build
```

`python3 dm/ios/tools/font_override.py <blizzardglobal.ttf 或 RomFS 目录> [font.ttf] out.ttf --weight N` 可在构建之外单独合成一份；`python3 dm/ios/tools/font_sample.py --weights 0 1 2 3 4 6 --sizes 20 28` 出样张（需要 PIL）：各档并排，再模拟图形页**渲染分辨率**上限——文字按缩小后的输出尺寸栅格化、整帧双线性放大（×1.43 ≈ iPhone Duo 内屏自动／均衡档，×1.66 ≈ 省电档）。产物写到 `$DM_ROOT/run/font-weight/`，不进仓库。

调低渲染分辨率后文字为什么变软、字体层面能做什么：界面层按上限后的输出尺寸渲染，游戏按相应更小的像素字号栅格化每个字，出图通道再把整帧双线性拉回屏幕。字体是矢量的，没有预渲染位图或字号表可以按放大倍数预补，所以字体本身无法给字形更多像素；只有让界面通道不受上限才行，那是渲染通道的改动，不在本功能范围内。字重能做的是不让楷体的细笔画在放大后淡到不足一个输出像素。建议取舍：高像素屏配自动／均衡档时用 3 档（真机选定的档），只有原生档下觉得偏重才降到 2 档。档位在构建时固定；按分辨率档位在启动时选不同字体是可能的后续工作，不在本次改动内。

真机：先后按 4 档、3 档出 iOS 包装到 iPhone Duo，4 档在高密度屏上太深，3 档被接受。此前 macOS App 在 1280x720 窗口里看过 2 档与 4 档。真机仍待检查：中英文设置页、任务日志、物品提示和秘境 HUD 在原生与自动分辨率下的文字；注意窄字段的裁切（笔画加长仍在同一字宽内，字宽不变，但上下各多出半档像素），以及 6 档以上的密集字。

### 渲染分辨率上限与测量包

图形页「渲染分辨率」滑块（`dm/host/dm_res_cap.h`、`dm_custom.c` 键 `render_res`、`front_ios.m` 的 `front_game_res`）由 `t_res_cap`（预算、宽高比、偶数、只缩不放、幂等，覆盖 Duo／17 Pro Max／iPad 尺寸）、`t_render_profile`（持久化、应用／放弃／默认、每次有效变更只通知一次重读）与 `test_touch_layout_options.py`（滑块行位于档位行之下、不与说明重叠）覆盖。Mac 宿主与 iOS 模拟器都走不到真机这条路；运行中切分辨率、出图线程放大、折叠／展开联动的真机验收仍待完成。

测量用 `DM_DIAG_SAMPLING=1 dm/ios/run.sh build` 出包（或在任意包的 `Documents/diag_sampling.txt` 放一个文件）。启动时 App 设置 `DM_NVN_PASSGPU`、`DM_THRCPU`（5 秒）、`DM_HEAT`（5 秒），写出 `Documents/diag/passgpu.tsv`、`thrcpu.tsv`、`heat.tsv`。逐通道计时会让提交线程等待 8 次提交之前的 GPU 完成，只作相对比较；`passgpu.tsv` 每个渲染通道一行，几分钟可达几十 MB。测量要拔线、固定亮度；充电状态下的读数不能用于功耗结论。

### 本机调试：在 Mac 上跑 iOS 包（代替模拟器）

iOS 模拟器 SDK 里没有 MetalFX 框架，图形后端编不过，着色器库也只有真机目标，所以模拟器这条路走不通。可行的本机路径是把 iphoneos 的 `DmIOS.app` 按“Designed for iPad”在 Apple 芯片 Mac 上原样启动（同 `tools/smoke_mac.sh` 的做法）：把构建产物包成 `<名>.app/Wrapper/DmIOS.app` 加 `WrappedBundle` 软链，`open -n <名>.app --env … --args -mode boot` 启动；描述文件要包含这台 Mac。容器在 `~/Library/Containers/<UUID>/Data`（按 `.com.apple.containermanagerd.metadata.plist` 或 `Documents/boot.txt` 找），把 RomFS 的 `data/` 克隆进 `Library/Application Support/romfs/`、测试存档放进 `Documents/save.test`。常用环境：`DM_TEST_SCREEN=2622x1206` 把屏幕当成 iPhone 16 Pro（配 `DM_TEST_SAFE_L/R` 安全区），`DM_SAVE_TEST=1`、`DM_TEST_ICLOUD_OFF=1`、`DM_KEYS` 进局、`DM_SCREEN_SHOT=<秒>:<文件名>` 整窗截图到 Documents。能验的是外壳、布局、分辨率与比例逻辑、进局；验不了真机触点、热态与 A 系列 GPU 时间。

### 无人值守功耗基准

`dm/ios/tools/power_bench.sh <每段分钟> <档位序列> [MetalFX] [存档备份目录]` 只启动一次游戏：用测试存档（`Documents/save.test`，绝不碰 `Documents/save`）、固定种子、进局并循环走动的按键脚本、每 90 秒轮换关卡（`DM_TEST_WARP_LV=every<拍>:<关卡…>`）、定时刷怪（`DM_TEST_SPAWN` 多条写法）和渲染分辨率时间表（`DM_TEST_RENDER_RES=<档>@<秒>,…`）。`heat.tsv` 每 5 秒多记电量、充电状态、低电量模式、渲染档与 MetalFX 档；`tools/bench_report.py` 按渲染档列分段，给每段的 %/小时及 ±(电量步长 ÷ 段时长) 的量化误差。电量读数是量化的：iPhone Duo 上观测到 5% 一档，10 分钟一段的误差约 ±30 %/小时。步长取 `--battery-step`，不给就从拔线数据推断并写明来源；充电中、混合状态、短于 10 分钟或样本不足的段不给速率，各段误差区间重叠时不给排名。要拔线、固定亮度跑；基准从第一次访问设备到最后拉回数据一直持有设备锁，不会结束已在运行的 App。

## 发布卫生

仅发布源码和文档。生成资源、字体、存档、设备截图、私有诊断、签名配置和密钥保留在公开目录之外。推送前检查新增提交的文件内容及作者／提交者元数据。提交问题反馈前先检查本地诊断是否含个人信息。

`main` 保留上游基线，`codex/plus` 包含增强预览。如需对照，请在自己的工作区构建相应分支。先备份存档；不要卸载持有唯一存档副本的应用。

字体构建注意：将 `DM_UI_FONT` 写入本机不入仓的 `dm/ios/local.env`，可在后续构建中保持选择。自选字体把已有字符映射到空白占位字形时，会回退到游戏原字形；语言选项使用较小字号并保持单行。

### 设置页保留性回归

设置页使用五个独立目的页：音频、游戏、游戏设定、图形、自定义。图形布局单独生成；不再替换原版游戏设定布局。新增路径插入仅接受未占用的首字节，生成后重新解析整棵资源路径树，核对所有原有路径与文件偏移保持不变。
